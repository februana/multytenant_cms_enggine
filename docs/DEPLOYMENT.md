# Deployment Guide

This repository supports two deployment paths that are implemented and tested in the checkout: **Docker Compose** and **native Ubuntu/Linux deployment** through `deploy/install.sh`. Both paths run the same PHP/SQLite CMS, use the same preset contracts, preserve the same optional-media semantics, and share the same backup, restore, update, and health-check scripts.

The repository does not include a Render Blueprint, Fly.io manifest, Railway configuration, Coolify/CapRover definition, or another managed-cloud adapter. A provider that can run the Docker image may be used as an operator-specific experiment, but it is not an officially tested target in this repository. For production, use Docker Compose with persistent volumes or the native installer on an Ubuntu/Linux host.

## Runtime model

The application is deployed to `/var/www/wedding`. In native mode, mutable state remains in that root by default. In Docker, the application code is immutable image content while mutable state is split into named volumes:

| Namespace | Docker path | Persistence role |
|---|---|---|
| CMS state | `/var/data` | Shared SQLite database containing tenant_configs, guest_links, RSVP, and users |
| Wedding and Theme Assets | `/var/www/wedding/uploads` | Tenant-prefixed media namespaces such as `tenant_<id>/cover`, gallery, backgrounds, music, and theme assets |
| Backups | `/var/www/wedding/backups` | Archives generated by `deploy/backup.sh` |
| WebDAV | `/var/www/wedding/webdav` | Optional WebDAV data when an operator provisions that integration |

The shared runtime contract in `deploy/runtime-directories.sh` creates the shared `uploads/`, `backups/`, and `webdav/` roots. Tenant-specific media directories are created on demand below `uploads/tenant_<id>/`; the installer and Docker entrypoint never mix files between tenants.

A clean checkout intentionally contains no administrator cover, music, Open Graph image, gallery, or preset-specific demo media. Those are deployment data, not required application code. The application suppresses optional media behavior when a valid local reference is absent, and the health check reports optional media as `WARNING` rather than manufacturing a dummy file.

## Docker Compose

### Prerequisites

Install Docker Engine with the Docker Compose plugin. Clone the repository and enter the checkout:

```bash
git clone https://github.com/februana/webserver_undangan.git
cd webserver_undangan
```

Create a local environment file and set a strong administrator password. Do not commit `.env`:

```bash
cp .env.example .env
chmod 600 .env
# Edit .env and set ADMIN_PASS to a strong value.
```

Compose refuses to start when `ADMIN_PASS` is empty or absent. The repository does not contain a shared production password.

### Build and start

```bash
docker compose build
docker compose up -d
docker compose ps
```

The image uses PHP 8.3 with Apache and installs GD with JPEG/WebP support, mbstring, PDO SQLite, SQLite3, ZipArchive, ImageMagick, and the Composer dependencies from `composer.lock`. Apache enables rewrite, headers, and expires modules. The image declares an HTTP `HEALTHCHECK`, and Compose repeats that check at the service level so Docker operators can see a `healthy` or `unhealthy` state.

Open the public invitation at `http://127.0.0.1/` and the admin UI at `http://127.0.0.1/admin/`. Run the application-level validator inside the container:

```bash
docker compose exec wedding-cms /var/www/wedding/deploy/health-check.sh
```

The image healthcheck only answers the process and frontend reachability question. The application-level validator additionally checks files, preset directories, active preset support, optional media, permissions, WebP processing, and sensitive-file blocking.

### Persistence and upgrades

Do not remove named volumes during a normal restart or upgrade:

```bash
docker compose down
docker compose up -d
```

Rebuild and recreate while retaining all CMS state, uploaded media, backup archives, and WebDAV data:

```bash
docker compose build
docker compose up -d --force-recreate
```

The following command intentionally deletes all named volumes and must only be used to reset a disposable test installation:

```bash
docker compose down -v
```

The Docker entrypoint initializes the shared SQLite path and runs the standalone `deploy/migrate.php` only when a main domain is configured. It preserves existing tenant data, applies `www-data` ownership, protects `.env`, and safely handles administrator credentials containing sed replacement characters when the initial environment file is created.

## Native Ubuntu/Linux deployment

### Prerequisites

The native installer requires a root-capable Ubuntu/Linux host and the following commands before it starts:

| Requirement | Purpose |
|---|---|
| `rsync` | Safe source and runtime synchronization |
| `openssl` | Credential generation and TLS-related operations |
| `composer` | Installation of locked PHP dependencies |
| Root or `sudo` | Package installation, web-server configuration, and `/var/www/wedding` ownership |

The installer then installs the selected Nginx or Apache web server and the required PHP runtime packages, including PHP-FPM/CLI, SQLite/PDO SQLite, GD, mbstring, ZipArchive, cURL, and supporting utilities.

### Fresh installation

Run the installer from the Git checkout. Do not create `/var/www/wedding` manually and do not run the installer from a directory containing untrusted files:

```bash
cd /path/to/webserver_undangan
sudo bash deploy/install.sh
```

The installer prompts for the primary domain and Super Admin username, generates the Super Admin password and encryption key, backs up existing Apache/Nginx configuration before replacement, deploys the repository to `/var/www/wedding`, runs `deploy/migrate.php`, configures the catch-all Apache site, and prints the one-time credentials summary. New tenant domains must be added manually from the Super Admin Dashboard.

After installation, run:

```bash
sudo /var/www/wedding/deploy/health-check.sh
```

The health check validates application files, all seven built-in theme adapters, the shared SQLite runtime, tenant uploads root, active preset support, ImageMagick or PHP GD WebP capability, permissions, ownership, web-server configuration, HTTP reachability, and public blocking of sensitive runtime data. Missing optional cover, music, or Open Graph media produce warnings; required runtime and security failures produce a non-zero exit status.

### Updating, backing up, and restoring

The update flow creates and validates a backup before replacing application code. It preserves `database.sqlite`, `.env`, the complete tenant-prefixed `uploads/` tree, `webdav/`, `backups/`, and legacy storage data. It then reruns the shared runtime contract, standalone migration, and health validation:

```bash
sudo /var/www/wedding/deploy/update.sh
```

For an explicit backup and restore operation:

```bash
sudo /var/www/wedding/deploy/backup.sh
sudo /var/www/wedding/deploy/restore.sh /path/to/backup.tar.gz
sudo /var/www/wedding/deploy/health-check.sh
```

`deploy/restore.sh` validates archive entries before changing the target, rejects path traversal and links, supports hidden files and filenames with spaces, and remains compatible with legacy WebDAV archive structure. Read [`BACKUP_RESTORE.md`](../BACKUP_RESTORE.md) for the complete disaster-recovery procedure.

## Health and security operations

The Docker image and Compose service use `curl http://127.0.0.1/` as their liveness/readiness signal. Operators should treat the following command as the authoritative CMS deployment audit:

```bash
/var/www/wedding/deploy/health-check.sh
```

For Docker, the equivalent is:

```bash
docker compose exec wedding-cms /var/www/wedding/deploy/health-check.sh
```

The web-server configuration and application rules block direct public access to `.env`, `database.sqlite`, backup artifacts, and WebDAV data. Keep administrator credentials outside Git, use TLS for public native deployments, and restrict WebDAV to operators who explicitly need it.

## Presets and visual customization

The active preset is `theme.theme_preset` inside the current tenant's `tenant_configs.config_json` value. The seven built-in presets are `dewankl`, `rainier`, `archak`, `parang`, `pawiwahan`, `shubh-vivah`, and `yami-buzzy`; `custom` is the CMS-native builder. Built-in presets intentionally retain different source-template section orders, DOM boundaries, dependencies, animation lifecycles, and capability sets.

The Admin panel exposes localized visual controls where a preset supports them, including section backgrounds, named color palettes, heading/body font catalogs, preset-specific Theme Assets, previews, reset-to-default actions, and the shared Media Manager. Resetting a visual reference removes the CMS selection while retaining the physical uploaded file, so the source-template fallback becomes active again. Custom mode remains the complete CMS-native section builder.

## Troubleshooting

If Docker refuses to start, verify that `.env` exists and contains a non-empty `ADMIN_PASS`, then inspect `docker compose logs wedding-cms`. If the container is `unhealthy`, first request `http://127.0.0.1/` from inside the container and then run the application-level health check. If a runtime directory is missing or unwritable, inspect the named volume mounts and rerun the container after correcting ownership; do not delete volumes unless resetting a test installation.

If a native deployment fails, rerun the prerequisite gate and inspect the generated Nginx or Apache virtual host before retrying. If optional media warnings appear, upload valid administrator media through the Admin UI rather than copying third-party sample assets. If a sensitive-file check fails, verify the generated server configuration and the repository's access-control rules before exposing the service publicly.
