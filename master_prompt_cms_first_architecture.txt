# MASTER PROMPT — CMS-FIRST ARCHITECTURE REFACTOR

## Peran

Bertindak sebagai senior software architect dan developer untuk melakukan refactor repository aplikasi undangan pernikahan berbasis PHP, SQLite, HTML, CSS, dan JavaScript.

Tujuan utama:

Membangun CMS yang menjadi sumber kebenaran utama untuk seluruh konfigurasi undangan, kemudian membuat frontend mengikuti kontrak CMS tersebut.

Gunakan pendekatan:

CMS → configuration contract → renderer → frontend

Jangan gunakan pendekatan:

frontend dibuat terlebih dahulu → kemudian CMS mencoba mengontrol frontend.

---

# ATURAN PALING PENTING

1. Jangan langsung mengubah kode.
2. Pada setiap phase, audit repository aktual terlebih dahulu.
3. Jangan mengandalkan asumsi dari percakapan atau dokumentasi lama jika berbeda dengan kode aktual.
4. Jangan menghapus fitur yang sudah bekerja tanpa alasan teknis yang jelas.
5. Jangan membuat ulang aplikasi dari nol.
6. Pertahankan kompatibilitas dengan data/configuration yang sudah ada jika memungkinkan.
7. Setiap perubahan harus diuji.
8. Jangan membuat setting CMS yang tidak benar-benar diterapkan frontend.
9. Jangan mempertahankan setting frontend yang seharusnya dapat dikontrol CMS tetapi masih hardcoded.
10. Semua pengaturan harus mempunyai jalur yang jelas:

CMS
↓
config.json
↓
configuration loader
↓
frontend renderer
↓
HTML/CSS

11. Live Preview dan website production harus menggunakan renderer/logic yang sama.
12. Jika sebuah setting dimatikan di CMS, frontend harus benar-benar berhenti merender bagian tersebut. Jangan hanya menggunakan display:none.
13. Jangan melakukan CSS optimization sebelum arsitektur CMS/frontend stabil.
14. Jangan menganggap sebuah phase selesai hanya karena kode sudah ditulis. Phase selesai hanya setelah audit dan testing berhasil.
15. Jangan mengubah phase berikutnya sebelum phase saat ini dinyatakan selesai.
16. Sebelum setiap phase, periksa kondisi repository aktual.
17. Jika menemukan perbedaan antara roadmap dan repository aktual, prioritaskan kondisi repository aktual dan jelaskan perbedaannya.
18. Jangan mengarang file, fungsi, endpoint, configuration key, atau fitur yang tidak ada.
19. Jika sebuah fitur sudah ada, evaluasi dan gunakan kembali sebelum membuat implementasi baru.
20. Hindari refactor besar tanpa alasan. Refactor hanya jika diperlukan untuk mencapai arsitektur CMS-first.

---

# MASALAH UTAMA YANG HARUS DISELESAIKAN

Repository sudah memiliki banyak fitur, tetapi beberapa setting CMS belum selalu benar-benar mengontrol frontend.

Contoh masalah:

- Love Story dapat dimatikan dari CMS tetapi masih muncul di frontend.
- Pengaturan ukuran background tidak selalu diterapkan.
- Pengaturan posisi background dapat tidak sinkron dengan frontend.
- Beberapa nilai visual masih hardcoded di frontend.
- CMS, config.json, JavaScript preview, PHP renderer, dan CSS belum selalu menggunakan kontrak yang sama.
- Live Preview dapat memiliki logic yang berbeda dari frontend production.
- Beberapa kontrol CMS berpotensi menjadi "setting palsu": terlihat dapat diubah tetapi tidak memberikan efek nyata.
- Beberapa default/fallback dapat berbeda antara config.php dan frontend.
- Ada kemungkinan endpoint CMS mengarah ke file yang tidak tersedia.

Masalah harus diselesaikan secara arsitektural, bukan sekadar ditambal satu per satu.

---

# PHASE 0 — REPOSITORY AUDIT & FREEZE

Sebelum mengubah file apa pun:

1. Periksa seluruh struktur repository.
2. Identifikasi:
   - frontend entrypoint
   - CMS entrypoint
   - configuration loader
   - configuration writer
   - section renderer
   - theme renderer
   - media system
   - preview system
   - API/endpoint
   - database
   - deployment
   - upload system
3. Periksa seluruh file PHP, JS, CSS, JSON yang relevan.
4. Jalankan PHP syntax check dengan:

php -l

5. Periksa konfigurasi JSON.
6. Identifikasi seluruh section frontend.
7. Identifikasi seluruh setting CMS.
8. Buat mapping:

CMS field
→ config key
→ backend handler
→ frontend consumer
→ CSS/HTML effect

9. Tandai setiap setting:
   - bekerja
   - sebagian bekerja
   - tidak bekerja
   - tidak memiliki consumer frontend
   - tidak memiliki handler backend
10. Tandai hardcoded visual value yang seharusnya berasal dari CMS.
11. Identifikasi configuration source yang duplikat atau saling bertentangan.
12. Identifikasi default/fallback yang berbeda antara backend dan frontend.
13. Identifikasi link, endpoint, file, atau action CMS yang tidak tersedia.
14. Jangan mengubah implementasi sebelum audit selesai.

Hasil Phase 0 harus berupa laporan audit yang menjelaskan:

- kondisi repository aktual
- arsitektur saat ini
- masalah
- risiko
- fitur yang sudah benar
- fitur yang perlu diperbaiki
- rekomendasi urutan implementasi

# PHASE 2 — CONFIGURATION CONTRACT

Setelah struktur CMS ditentukan, tentukan struktur configuration.

CMS adalah sumber kebenaran.

Gunakan struktur yang jelas, konsisten, dan mudah dipetakan.

Minimal mencakup:

wedding
couple
parents
schedule
location
sections
love_story
gallery
gift
rsvp
messages
music
theme
seo

---

## Section visibility

Gunakan satu sumber kebenaran:

{
  "sections": {
    "cover": true,
    "opening": true,
    "couple": true,
    "schedule": true,
    "love_story": false,
    "gallery": true,
    "gift": true,
    "location": true,
    "rsvp": true,
    "messages": true,
    "music": true
  }
}

Jangan membuat beberapa sumber berbeda untuk visibility section.

Jika sebuah section memiliki enabled=false, seluruh frontend harus mengikuti nilai tersebut.

# PHASE 3 — CMS CRUD & VALIDATION

Setiap form CMS harus mengikuti:

Form
↓
Normalize
↓
Validate
↓
Save
↓
Read back
↓
Verify

Contoh:

Pengguna mematikan Love Story.

CMS:
sections.love_story = false

Backend harus menyimpan:

sections.love_story = false

Setelah save, backend membaca kembali configuration dan memastikan nilainya benar.

Jika gagal:

"Pengaturan gagal disimpan."

Jangan menampilkan pesan sukses palsu.

Semua input harus divalidasi.

Validasi harus mencakup:

- tipe data
- range
- allowed values
- panjang string
- file type
- file size
- URL bila relevan
- enum/status
- struktur array/object

---

# PHASE 4 — FRONTEND SECTION RENDERER

Frontend harus mengikuti configuration CMS.

Pola:

if section.enabled:
    render section
else:
    do not render section

Jangan menggunakan CSS display:none sebagai mekanisme utama untuk section disabled.

Contoh:

sections.love_story = false

Maka HTML Love Story tidak boleh dibuat.

Semua section harus mengikuti mekanisme yang sama.

# PHASE 7 — MEDIA & BACKGROUND SYSTEM

Satukan sistem media.

Jenis media minimal:

- Cover
- Background
- Gallery
- Music
- Love Story
- Gift

Untuk background, CMS harus dapat mengontrol:

- gambar
- ukuran
- posisi
- repeat
- attachment jika diperlukan
- overlay jika tersedia

Struktur yang disarankan:

background
├── image
├── size
├── position
├── repeat
└── overlay

Contoh:

Jika pengguna memilih:

"Penuhi area"

frontend harus menggunakan:

background-size: cover

Jika memilih:

"Tampilkan seluruh gambar"

frontend harus menggunakan:

background-size: contain

Tidak boleh ada nilai hardcoded yang mengalahkan setting CMS.

Pastikan desktop dan mobile dapat memiliki konfigurasi yang berbeda jika UI CMS memang menyediakan pengaturan tersebut.

# PHASE 8 — LIVE PREVIEW

Live Preview harus menggunakan frontend renderer yang sama dengan production.

Jangan membuat frontend preview dengan logic yang berbeda.

Target:

CMS state
↓
Frontend Renderer
↓
Preview

dan:

CMS state
↓
Frontend Renderer
↓
Production Website

Jika pengguna mematikan Love Story di CMS:

Preview harus menghilangkannya.

Jika background size diubah:

Preview harus langsung berubah sesuai konfigurasi.

Preview tidak boleh menjadi implementasi frontend kedua yang terpisah.

# PHASE 9 — AUTOMATED CMS ↔ FRONTEND TESTING

Buat test matrix.

Minimal:

Love Story OFF
→ config false
→ HTML Love Story tidak ada
→ preview tidak ada

Love Story ON
→ config true
→ HTML Love Story ada
→ preview ada

Gallery OFF
→ config false
→ HTML Gallery tidak ada

Background Cover
→ config cover
→ frontend cover

Background Contain
→ config contain
→ frontend contain

Hero 80vh
→ config 80vh
→ frontend 80vh

Music OFF
→ config false
→ music tidak dirender

Tambahkan test untuk setiap setting penting.

Bila memungkinkan, buat automated audit yang dapat menemukan:

CMS field tanpa config key
CMS field tanpa backend handler
config key tanpa frontend consumer
frontend setting tanpa CMS control
dead action
dead endpoint
hardcoded value yang seharusnya configurable

# PHASE 10 — CMS UX

Setelah functionality benar, sempurnakan CMS untuk orang awam.

Setiap setting penting harus mempunyai:

1. Nama sederhana.
2. Deskripsi singkat.
3. Nilai default aman.
4. Preview jika memungkinkan.
5. Status ON/OFF yang jelas.

Contoh:

## Ukuran Gambar Sampul

### Penuhi area
Gambar memenuhi seluruh area sampul. Sebagian gambar mungkin terpotong.

### Tampilkan seluruh gambar
Seluruh gambar terlihat, tetapi mungkin terdapat ruang kosong.

### Ukuran asli
Gunakan ukuran asli gambar.

Gunakan istilah yang mudah dipahami.

# PHASE 12 — CSS OPTIMIZATION

Hanya dilakukan setelah seluruh phase sebelumnya selesai.

Tujuan:

- menghapus CSS duplikat
- menghapus inline CSS yang tidak diperlukan
- menyatukan CSS variables
- mengurangi selector berlebihan
- memperbaiki responsive CSS
- mengoptimalkan ukuran CSS
- mempertahankan seluruh fungsi CMS

Jangan mengorbankan functionality demi optimasi.

---

# DEFINITION OF DONE

## CMS

- Semua setting memiliki fungsi nyata.
- Tidak ada setting palsu.
- Bahasa CMS mudah dipahami.
- Save selalu diverifikasi.
- ON/OFF bekerja.
- Setiap action memiliki backend handler.
- Setiap field memiliki validasi.

## Configuration

- config.json atau configuration source yang disepakati menjadi single source of truth.
- Tidak ada configuration source yang saling bertentangan.
- Tidak ada setting CMS yang tidak memiliki consumer.

## Frontend

- Semua section mengikuti sections.
- Disabled section tidak dirender.
- Theme mengikuti configuration.
- Background mengikuti setting CMS.
- Responsive behavior mengikuti konfigurasi yang relevan.
- Tidak ada hardcoded value yang mengalahkan configuration.

## Preview

- Preview dan production menggunakan renderer yang sama.
- Perubahan CMS tercermin pada preview.

## Quality

- Tidak ada PHP syntax error.
- Tidak ada broken endpoint.
- Tidak ada tombol CMS tanpa handler.
- Tidak ada setting yang disimpan tetapi tidak pernah digunakan.
- Tidak ada hardcoded visual value yang mengalahkan CMS.
- Tidak ada regresi terhadap fitur yang sebelumnya sudah bekerja.

---

# PRIORITAS

Jika harus memilih antara:

1. menambahkan fitur baru,
2. mempercantik CMS,
3. memperbaiki hubungan CMS dan frontend,

selalu pilih nomor 3.

Aplikasi yang memiliki lebih sedikit fitur tetapi setiap setting bekerja dengan benar lebih penting daripada CMS yang memiliki banyak opsi tetapi sebagian tidak berefek.

---

# MODE KERJA

Jangan melakukan perubahan besar sekaligus.

Kerjakan satu phase pada satu waktu.

Untuk setiap phase:

1. Audit kondisi aktual.
2. Jelaskan masalah.
3. Jelaskan rencana.
4. Implementasikan.
5. Jalankan test.
6. Periksa regresi.
7. Tampilkan daftar file yang berubah.
8. Tampilkan hasil test.
9. Nyatakan apakah phase benar-benar selesai.
10. Jangan lanjut ke phase berikutnya jika masih ada bug kritis.
